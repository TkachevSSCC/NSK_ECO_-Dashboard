# Пояснительная записка

**Обозначение:** НСКЭКО.003.ПЗ
**Наименование:** «NSK Eco Dashboard»
**Версия:** 1.0, проект

## 1. Назначение документа

Документ описывает принятые в Программе архитектурные и алгоритмические решения и дополняет описание программы.

## 2. Архитектура

Программа построена по клиент-серверной схеме. React-клиент отображает данные и передаёт команды через HTTP API. FastAPI backend обрабатывает запросы, взаимодействует с сервисным слоем и базой данных и публикует текущие метрики через WebSocket. Фоновая петля метрик запускается при старте backend. Интеграция СИГМА запускается в составе backend и использует очередь исходящих событий.

PostgreSQL содержит долговременные записи станций и связанные сущности. Redis применяется для временного состояния, включая переопределения загрязнения, а также как брокер/хранилище Celery и основа outbox согласно конфигурации. Celery worker и beat запускаются отдельными процессами.

## 3. Основные расчёты

### 3.1. Сетевые метрики

Цикл обновления метрик имеет интервал `TICK_SECONDS = 1` секунда. Для каждого тика выбираются активные станции с зарядом больше нуля. В зависимости от режима передачи определяется число сообщений в глобальную сеть; остальные активные станции формируют зональный обмен. Рассчитываются объём трафика, параметры буфера и потери при превышении его ёмкости.

Базовые веса сообщений по умолчанию составляют 1,0 КБ для глобальной сети и 0,4 КБ для локальной зоны. Вес корректируется ступенчато по сумме PM2.5 и PM10. Значения можно менять через интерфейс в допустимом диапазоне, определённом backend.

### 3.2. Заряд

В расчётной модели стационарные устройства не разряжаются от передачи. Для движущихся устройств применяются ставки 0,1 процентного пункта за сообщение в глобальную сеть и 0,06 процентного пункта за сообщение в зоне; предусмотрен случайный разброс ±5%. Для устройств опасного временного кластера расход глобальной передачи масштабируется коэффициентом алгоритма. Это параметры модели, а не физически измеренная характеристика оборудования.

### 3.3. Кластеризация и загрязнение

Backend поддерживает режим передачи всеми активными станциями и режим передачи через кластерные головы с учётом расположения станций. Сценарий превышения загрязнения и искусственное загрязнение предназначены для демонстрации поведения системы. Сравнение сценариев рассчитывает предполагаемую нагрузку без обязательного изменения текущего состояния.

### 3.4. Тепловая карта

Клиентская часть формирует поле тепловой карты на основе доступных значений станций и области анализа, отображает предложенные места установки и формирует PDF. Выход является визуализацией модели и зависит от исходного набора данных.

## 4. Интеграция с СИГМА

При включённой интеграции backend формирует события перехода загрязнения станции, нормализации, сетевые снимки и сетевые предупреждения. События ставятся в исходящую очередь, ограничиваются кулдаунами и частотным лимитом и повторяются при временных ошибках согласно настройкам. Неустранимые клиентские ошибки переводятся в dead-letter. Секреты платформы должны находиться только в серверном окружении.

Параметры подключения и перечень типов событий документированы в корневом README проекта и `.example.env`. Для эксплуатации нескольких экземпляров backend необходимо отдельно проверить согласованность фонового цикла и outbox: текущая реализация рассчитана на один процесс приложения.

## 5. Ограничения и допущения

- Программа не заменяет сертифицированный комплекс измерений и не устанавливает метрологическую достоверность данных.
- Производительность и ёмкость не нормированы до испытаний на целевой конфигурации.
- Реальная интеграция с СИГМА требует регистрации приложения/источника, корректных сетевых разрешений и учётных данных.
- Пользовательская авторизация и разграничение ролей не подтверждены текущей реализацией; доступ к среде должен контролироваться инфраструктурой.
- Данные CO2 загружаются отдельным HTTP-источником, но их доступность не является условием работы основной панели.
